# Reference notes: `pascalLangdock/elevenlabs_hack` (CORE-05)

Read on 31 Oct 2026 (last push 11 Dec 2025). **No license, so this is a design reference only: ideas
below are written in our own words, and no code was copied.** The repo is 8 small files; the page
reading and clicking happen inside the `browser-use` package, so there is no page-state code to study.

- **Structure:** `backend/main.py` (FastAPI: `POST /execute`, `POST /elevenlabs-tool`, `GET /health`, port 8000), `browser_manager.py` (one class around a browser-use agent), `voice_client.py` (an ElevenLabs cloud voice session), `start_chrome_debug.sh`, `save_auth.py`, and two Gmail test scripts. Voice is cloud-side; the backend only receives a text command and returns a text result.
- **How the agent starts:** a brand-new agent and browser handle are created for every command, capped at 5 steps, and the final result string is returned. No memory between commands. Ours keeps task memory across a 30-step task.
- **Browser connection:** it attaches over CDP (`CHROME_CDP_URL`, default `localhost:9222`) to a Chrome the user starts with a script: remote debugging on port 9222, a **separate dedicated `--user-data-dir`** (not the main profile), first-run prompts off, opening Gmail. The user signs in to Gmail once in that window and leaves it open. The path is hard-coded for macOS and the profile is in `/tmp`, which does not survive a reboot.
- **Gmail login:** two scripts tried to sign in with an automated browser and save the session. The second one uses real Chrome, hides the automation flag and fakes the user agent, which suggests Google was blocking the automated sign-in. The test scripts then ask plain questions through the CDP-attached Chrome ("how many unread emails", "who sent the last 3 emails").
- **Prompt idea to borrow:** every task is followed by a request to describe the current page for a blind user: page title and URL, the key content (headings, main text), and the available actions, kept short. We should end tasks, `read_page(summary)` and "where am I" the same way, using the `summary`, `headings`, `links` and `buttons` fields we already have in the snapshot.
- **Task D implications (for BRW-07, #33):** (1) CDP attach with a dedicated Chrome profile that the user signs in to once is the approach that worked there, so "your own Chrome" in practice means a separate debug profile, not the everyday one. This agrees with Chrome restricting remote debugging on the default profile, but we must verify it on the demo machine. (2) Use a profile folder that persists, not `/tmp`, and make the launch command per-OS. (3) Do **not** copy the automation-hiding tricks: they are bot-protection evasion, which our rules forbid, and the human signs in by hand anyway. (4) Reusable test questions: unread count, senders of the latest 3 emails.
- **Do not borrow:** the server binds `0.0.0.0` with CORS `*` and no authentication on an endpoint that drives a logged-in browser. Ours binds `127.0.0.1` and takes input only from the Console WebSocket. It has no domain policy, no irreversible-action hold, no confirmation, no verification and no human hand-off, which are our whole point. A hard-coded cloud agent id, and errors returned as raw exception text, also stay out.
- **Takeaway:** it confirms our scope gap (everything after "command in, text out") and gives us one proven connection method for Task D. Nothing here changes the 3.1 plan.
